## 2. 이 앱이 필요한 이유

사용자는 여행에서 어디에 다녀왔는지 기록하는 용도로 트리플을 사용했다. 이제 직접 오래 사용할 여행 다이어리를 만들고 싶어 한다. 장소에 사진과 소감을 남기고, 날짜별 일기를 쓰며, 여행·기간으로 묶어 보고, 다녀온 장소가 지도에 차곡차곡 쌓이는 경험이 핵심이다.

첫 버전은 소유자 한 명이 쓰는 비공개 웹앱이다. 여행 계획·예약·맛집 추천·SNS 플랫폼으로 확대하지 않는다. 사용자가 편하게 실제 기록을 쌓고, 나중에 데이터를 꺼내 옮길 수 있어야 한다.

### 후속 확정: 아이폰 중심 웹앱·PWA와 맥 사용 (2026-10-31)

사용자는 아이폰을 주 사용 기기로 하고 맥에서도 같은 기록을 사용하는 방향을 선택했다. 아이폰 Safari·홈 화면 실행에서 사진·장소·일기를 기록하고, 맥의 Safari·Chrome 브라우저에서는 같은 웹앱으로 조회·수정·사진과 긴 글 정리를 한다. 별도 iOS·macOS 네이티브 앱이나 App Store 배포로 전환하지 않는다.

기기 간 데이터는 같은 계정의 서버 기록·사진을 공통 원본으로 사용한다. 브라우저 임시 저장을 동기화로 표현하지 않는다. 온라인 사용과 글 초안 복구를 우선하고 완전한 오프라인 사용·백그라운드 사진 업로드는 1차에서 제외한다. 업로드 중 앱을 벗어났을 때 중단·실패와 재시도를 안내한다.

PWA 이름·아이콘·시작 URL·standalone 구성, 아이폰 사진 선택·한글 입력·키보드·safe area, 맥 브라우저의 넓은 화면·키보드 접근을 검증한다. 아이폰 저장 → 맥 조회·수정 → 아이폰 재조회 시나리오를 실제 서버 저장과 함께 확인한다. 에뮬레이션과 실기기 확인 결과를 구분한다. 세부 기준은 PRD §2.1과 DECISIONS.md를 따른다. 이 기획 변경은 설치·동기화 구현 완료를 뜻하지 않는다.

## 3. 사용자 표현 그대로 기억할 요구사항

> 다이어리니까 월간, 주간, 일간 연동이 되면 좋겠어! 월간엔 기간이 보이고 주간엔 디테일, 일간엔 일기를 쓰면 좋겠네! 정갈한 폰트쓰고

> 종이 다이어리를 보면 주간은 한 두페이지정도에 일주일이 한번에 보인다는걸 명심해

> 월간에 표시할때도 긴 띠가 보이는건 좋은데 왼쪽 세로선은 싫어

> 너무 과한 감성문구보다는 깔끔하고 직관적으로

> main 브랜치는 무조건 pr올려야하는 규칙

이 요구를 장식적인 여행 감성 화면으로 재해석하지 않는다. 특히 주간 전체 보기는 단순한 스타일 선호가 아니라 화면의 기능적 목적이다.

## 4. 화면별로 서로 다른 역할

| 보기 | 핵심 역할 | 표시 내용 |
| --- | --- | --- |
| 월간 | 언제 여행했는지 | 한 달 달력, 여행 기간의 긴 옅은 가로 띠, 기록 표시 |
| 주간 | 일주일 동안 어디를 갔는지 | 7일 고정 칸에 장소·시간·작은 사진 요약 |
| 일간 | 하루를 자세히 읽고 쓰기 | 여러 방문 기록, 큰 사진, 장소별 소감, 하루 일기 |
| 여행 | 특정 여행을 모아보기 | 기간·대표 사진·여행 내 일간 기록·여행 지도 |
| 지도 | 방문 장소가 쌓이는 모습 | 전체/여행/기간 필터, 사진 핀, 재방문 이력 |

### 월간

기간 띠에 왼쪽 세로 강조선을 절대 넣지 않는다. 선 없이 옅은 면색이 이어지게 한다. 이름은 시작 지점에 두고 주/월 경계에서도 기간이 이해되게 한다. 월간에 글·사진을 과하게 채우지 않는다.

### 주간 — 첫 수정 대상

첫 시안은 날짜 선택 막대 아래 해당 하루의 기록만 보여줘 일간과 구분되지 않았다. 사용자가 지적했고 이 방식은 폐기했다. 수정 시안은 두 열에 7일을 배치하고 마지막 여분 칸을 주간 요약으로 사용했다. 사용자는 방향은 마음에 들어 했지만 여전히 잘림을 지적했다.

따라서 7일이 한눈에 들어오는 구성을 유지하면서 잘림과 가독성을 먼저 해결한다. 하루씩 길게 늘어지는 타임라인이나 스와이프로 하루만 보는 방식은 주간의 대체안이 아니다. 모바일에서 가용 높이는 헤더·탭·하단 메뉴·safe area·주소창 상태를 포함해 계산한다. 높이만 줄이고 overflow:hidden으로 기록을 잘라내지 않는다. 사진·장소 노출 개수를 줄이더라도 '+N개'가 접근 가능해야 한다.

실제 iPhone Safari와 작은 화면에서 확인하고, 사용자 화면을 확인하지 않았다면 '모바일 검증 완료'라고 보고하지 않는다. 360/390px은 폭의 기준일 뿐 높이까지 검증해야 한다. 극히 작은 화면의 확대 접근 방법은 사용성을 검토해 정한다.

### 일간과 기록 구조

하루에 카페 → 산책길 → 식당 등 여러 장소를 갈 수 있다. 장소별 방문마다 사진 여러 장과 소감을 남기고, 하루 전체 일기는 별도로 쓴다. 시간이 없어도 기록 가능하고 표시 순서를 지정할 수 있게 한다.

### 지도

장소를 일기에 저장하면 지도에도 자동 반영한다. 대표 사진을 핀처럼 보여주되 멀리서는 장소 묶음으로 정리한다. 핀에서 미리보기와 해당 일기로 들어간다. 같은 장소의 재방문은 별도 방문 기록으로 남긴다. GPS 이동 자동 추적은 요구하지 않았다.

## 5. 이름·로고·시각 방향

- 이름: 트립로그 / triplog. 개발자에게 익숙한 '로그'와 여행 기록의 의미를 결합했다.
- 로고: 개발자 터미널 창의 >_ 앞을 비행기가 가로질러 나오는 형태. 공항 터미널 건물로 해석하지 않는다.
- 소문자 triplog 워드마크, 읽기 쉬운 SUIT, 생크림색에 가까운 밝은 바탕, 얇은 구분선.
- 메인 컬러는 몽블랑 디저트의 밤크림색으로 확정했다. 기존 파란색 중심 방향을 대체하며, 옅은 밤크림은 기간 띠·선택 배경에, 진한 밤색은 버튼·선택 글씨에 사용한다. DECISIONS.md의 팔레트는 화면 검증 전 초안이며 기존 시안·SVG에 반영된 것으로 간주하지 않는다.
- 초안의 회색 배경·파란 버튼·둥근 카드 반복이 '토스 같다'는 피드백을 받았다. 해당 스타일로 되돌리지 않는다.
- 감성은 사진과 배치에서 만들고, 과한 슬로건·손글씨·장식은 넣지 않는다.
- 생성된 로고와 시안 헤더의 SVG 재현은 서로 동일한 원본이 아니다. 시안 SVG를 승인된 최종 로고 파일이라고 간주하지 않는다. 실제 에셋을 확보하고 필요한 아이콘 크기·단색·투명 배경 버전을 정리하는 작업은 별도 확인한다.

## 6. 시안이 한 일 / 하지 않은 일

### 구현된 것은 디자인 검토용이다

- 정적 HTML/CSS/JavaScript, 가상 교토 여행 데이터
- 월간/주간/일간/여행/지도 보기 전환
- 직접 입력한 방문 기록과 하루 일기의 브라우저 localStorage 저장
- 샘플 장소 사진 핀을 누르면 일간으로 이동
- 작은 터미널+비행기 SVG 심벌

### 실제 운영 기능으로 오해하면 안 되는 부분

- 지도는 CSS/SVG로 그린 배치 시안이며 Google Maps가 아니다. 실제 장소 검색·좌표·클러스터링은 없다.
- 저장은 서버 동기화가 아니다. 브라우저 삭제·기기 변경에 대한 내구성이 없다.
- 사진 업로드 시안은 1장/3MB 제한의 로컬 파일 읽기일 뿐이다. 이는 확정된 제품 정책이 아니다.
- 샘플 사진은 외부 Unsplash 이미지다. 실제 방문 증거·소유자 사진·최종 에셋이 아니다.
- 여행 관리·대표 사진·필터·재방문 묶음·삭제·백업·복원 등의 운영 기능은 완성되지 않았다.
- 지도는 샘플 데이터만 표시하고 새로 추가한 로컬 기록의 위치를 반영하지 않는다.
- 시안의 집계 숫자와 여행 정보 일부는 하드코딩이다.
- Sites의 개인 접근 게이트는 실제 앱의 API/저장소 소유권 검증을 대신하지 않는다.

시안은 화면 의도를 참고하는 자료로 사용한다. 그대로 생산 환경으로 배포하기보다 컴포넌트·데이터·API·검증을 분리한 실제 앱으로 만든다. 이 문서만으로 시안 소스나 이미지 원본이 GitHub에 포함되는 것은 아니다. 임시 실행 환경 경로는 다른 Codex 세션에서 접근 가능하다고 가정하지 않는다.

## 7. 데이터 모델에서 지킬 의미

PRD의 테이블은 구현 제안이며 확정 스키마가 아니다. 기술 선택 후 모델을 구체화한다.

- 장소(Place)와 방문(Visit)은 분리한다. 카페 한 곳에 세 번 가면 장소 하나와 방문 세 개다.
- 하루 일기와 장소별 소감을 한 필드에 섞지 않는다.
- 월간·주간·일간은 동일한 원본 기록을 투영한다. 각 화면마다 별도 복제 데이터를 편집하지 않는다.
- 현지 날짜를 보존하고 시간 입력은 선택이다. UTC 변환 때문에 여행 일자가 달라지면 안 된다.
- 여행 기간 변경으로 기존 기록을 자동 삭제하지 않는다.
- 장소명을 직접 입력할 수 있어야 한다. 좌표가 없으면 기록은 남기고 지도 제외 상태를 안내한다.
- 공유를 고려해 소유자·작성자 식별은 남기되, 공동편집 기능을 미리 구현하지 않는다.
- 같은 날짜의 복수 여행, 여행 없는 기록, 장소 중복 병합 규칙은 #1에서 결정한다.

## 8. 권장 기술 구성과 남은 결정 (2026-10-31 추가)

사용자는 아래 추천을 인수인계 문서에 남겨달라고 요청했다. 다음 개발의 **권장 기준안**으로 사용한다. 이 기록은 클라우드 프로젝트 생성·유료 결제·외부 계정 연결 또는 배포가 이미 완료됐다는 의미가 아니다. 사진 압축 수치 등 검증이 필요한 정책은 제안 상태로 유지한다.

### 권장 스택

| 영역 | 권장 구성 | 선택 이유 |
| --- | --- | --- |
| 화면·서버 기능 | Next.js + TypeScript | 화면과 필요한 서버 처리를 한 저장소에서 관리 |
| 디자인 | Tailwind CSS + 직접 만든 다이어리 컴포넌트 | 월간 기간 띠와 주간 7일 고정 칸을 요구대로 조정 |
| DB | Supabase PostgreSQL | 여행·일기·장소·방문 관계 저장 |
| 인증 | Supabase Auth + Google 로그인 | 소유자 계정만 접근하는 로그인 구성 |
| 사진 | Supabase Storage 비공개 버킷 | 사진·썸네일과 소유자 접근 권한 관리 |
| 지도 | Google Maps | 장소 검색·방문 사진 핀 구현 |
| 소스·배포 | GitHub + Vercel | 작업 브랜치·PR 검토와 배포 흐름 연결 |

특정 UI 라이브러리의 기본 달력을 그대로 적용해 주간 의도를 바꾸지 않는다. 달력 컴포넌트는 제품 요구에 맞게 직접 구성하되 검증된 날짜 계산 도구는 사용할 수 있다. Next.js·Supabase 패키지는 착수 시 공식 문서와 호환 버전을 확인하고 lockfile을 커밋한다. 서버 처리는 Next.js 프로젝트 안에서 시작하고, 별도 백엔드 서버 추가는 실제 필요가 생겼을 때 검토한다.

### 프로젝트와 권한 분리

트립로그 전용 프로젝트로 구성한다. 차곡의 운영 DB·사진·비밀값을 재사용하거나 섞지 않는다. 개발/미리보기와 운영의 데이터·비밀값도 분리한다.

Google 로그인 성공만으로 접근을 허용하지 않고 소유자 허용 여부를 서버에서 검증한다. DB 및 사진에 소유권 정책(RLS 등)을 적용하며 서비스 비밀키를 브라우저에 노출하지 않는다. 인증·저장 정책을 실제 요청으로 검증한다.

### 사진 저장 기준 제안

- 첫 버전에는 보기 좋은 크기의 압축본과 작은 썸네일을 저장하는 방식을 추천한다.
- 긴 변 최대 약 2,048px은 **검증할 제안값**이다. 실제 아이폰 사진의 화질·용량·회전·HEIC 처리를 확인한 후 정한다.
- 원본 사진은 사용자의 휴대폰/개인 사진 백업에 보관하는 전제다. 앱은 원본 백업 서비스라고 안내하지 않는다.
- 앱에서 원본까지 보관할지는 아직 결정하지 않았다. 압축 손실을 안내하고 원본 보관·업로드 제한·품질·사진 개수는 #1에서 정리한다.
- 시안의 1장/3MB 제한은 운영 정책으로 승계하지 않는다.

### 저장·복구와 비용

글은 서버 자동 저장과 브라우저 임시 복구를 함께 설계하고 저장 실패를 구분한다. 내보내기는 JSON과 사진을 함께 제공해 다른 서비스로 이전할 수 있게 하며 복원으로 검증한다.

개인 비상업용 운영에 Vercel Hobby를 우선 검토하되 최신 이용 조건을 확인한다. DB·사진 저장/전송·지도 호출까지 비용을 따로 산정한다. 특정 무료 플랜으로 영구 무료 또는 무제한 사진 저장이 된다고 가정하지 않는다. 유료 가입·비용 발생 변경은 필요한 계정과 예산을 확인한다.

### 권장 구현 순서

1. #1에서 위 기준과 미결정 정책을 정리하고 #2의 프로젝트·DB 모델·개인 로그인을 구성한다.
2. #4·#5의 여행·일기를 서버에 저장해 휴대폰과 맥에서 다시 읽는 흐름을 완성한다.

#3 주간 잘림 개선과 #6 월간 연동은 이 과정에서 함께 진행한다. 완성 후로 미루지 않고 7일 전체 보기 기준을 계속 검증한다.

### 여전히 결정할 항목과 문서 일치

주 시작 요일, 여행 없는 기록, 같은 날 복수 여행, 장소 중복 병합, 사진 원본·형식·용량·개수·압축 품질, 휴지통 기간, 검색 1차 포함, 월 예산은 결정 전이다.

PRD v1.0·README·#1에는 초기의 '기술 스택 미정' 표현이 남아 있을 수 있다. 이 절을 후속 추천 기준으로 함께 읽고, #1의 결정 작업에서 최종 선택을 PRD·README·이슈에 일치시킨다. 이 문서 변경만으로 #1을 닫지 않는다. 핵심 정책만 짧게 묻고 되돌릴 수 있는 구현 세부사항까지 매번 질문하며 멈추지 않는다.

## 9. 지금은 하지 않을 것

공유 링크, 초대 사용자 조회, 동행자 공동 작성은 후속 아이디어다. 사용자는 1차에서 제외했다. 아이폰 캘린더 연동도 제외했다. iOS 네이티브 앱/앱스토어 배포를 진행하지 않는다. 트리플 이관 여부는 사용자가 고민 중이다. 이동 추적·예약·추천·가계부·AI 여행 추천을 범위에 추가하지 않는다.

한 이슈 또는 검토 가능한 범위별로 PR을 만든다. 구현되지 않은 나머지 이슈까지 closes로 연결하지 않는다. 문서만 추가한 PR로 #1~#12를 완료 처리하지 않는다. 실제 검증 후 진행표를 갱신한다.

## 11. 브랜치·PR 운영 — 반드시 준수

**main에 직접 커밋·푸시하지 않는다. 문서 수정도 작업 브랜치 → PR로 진행한다.** 사용자 요청은 모든 main 변경에 PR 필수다.

중요한 현황: 대화에서 브랜치 보호 설정 방법을 안내했지만, 연결 도구는 보호 설정을 지원하지 않았고 브라우저는 로그아웃 상태였다. 따라서 서버 측 보호 규칙이 실제 적용됐다고 확인하지 못했다. Codex는 설정 완료로 단정하지 말고 가능하면 read-only로 상태를 확인한다. 설정이 없더라도 main 직푸시를 하지 않는다.

설정 제안은 main 대상 PR 필수, 승인 리뷰 필수 해제(개인 개발), 관리자 우회 금지, force push/삭제 비허용이었다. 이는 안내한 제안이며 설정 적용 증거가 아니다. 유효한 CI가 생기면 요구할 체크 이름을 확인한 뒤 보호 설정과 연결한다. 존재하지 않는 체크를 필수로 걸어 머지를 막지 않는다.

브랜치 예: feat/5-daily-visits, fix/3-weekly-layout, docs/setup. PR에는 바뀐 동작, 관련 이슈, 실행한 검증과 미검증 한계를 적는다. 사용자에게 PR URL을 전달한다. 자동 머지·보호 우회는 이 문서로 승인된 것으로 간주하지 않는다.

PR·이슈 제목 앞에는 작업 성격에 맞는 개발용 이모지를 붙인다. 예: `✨ feat:`, `🐛 fix:`, `📝 docs:`, `🔧 chore:`. 이슈의 기존 영역·우선순위 표시는 유지한다. 이모지는 기존 라벨 선택과 적용 확인을 대신하지 않는다. 완료 조건을 모두 충족한 이슈만 닫고 부분 구현은 남은 검증과 함께 열린 상태로 관리한다. PR 머지 후 실제 반영 여부와 진행표 #12를 함께 확인한다.

## 12. 저장과 운영의 완료 기준

- 허용 계정만 접근하고, 서버의 모든 조회/수정/파일 접근에서 소유권을 확인한다.
- 사진 저장소를 비공개로 운영하고 업로드 진행/실패/완료를 구분한다.
- 미리보기·운영 환경변수/DB/파일을 분리하고 운영 데이터에 테스트를 수행하지 않는다.
- 원본 사진·일기·개인 위치·비밀키는 공개 GitHub에 넣지 않는다. 기획서와 이슈는 제품 설계 정보만 가진다.
- Google Maps 연동 시 해당 API의 공식 저장/표시/사용량 정책을 확인한다. API 키는 의도한 API와 도메인으로 제한한다.
- 내보내기 파일에 날짜·장소·좌표·소감·사진 연결을 담고 실제 복원으로 검증한다. 단순 다운로드 성공으로 백업 완료라고 하지 않는다.
- 비용은 Vercel뿐 아니라 DB·사진 저장/전송·지도 호출·도메인까지 따로 확인한다. 영구 무료를 약속하지 않는다.

## 13. 검증 체크리스트

- 5일 여행이 월간에서 주/월 경계에 걸쳐 올바르게 이어지며 왼쪽 세로선이 없다.
- 모바일에서 한 주 7일과 마지막 칸·+N개가 접근 가능하고 큰 글씨/주소창 변화에도 핵심 기능이 막히지 않는다.
- 같은 날 세 장소와 하루 일기를 저장하고 사진·소감·순서를 구분해 다시 본다.
- 지도/주간에서 선택한 기록의 일간으로 이동한다.
- 같은 장소 두 번 방문 이력을 지도에서 확인한다.
- 좌표/사진/시간 없는 기록 및 빈 목록을 처리한다.
- 해외 날짜가 한국 기기에서 바뀌지 않는다.
- 새로고침·기기 변경 후 서버 기록이 유지되고 네트워크 실패 후 초안을 복구한다.
- 동시 수정 시 조용히 덮어쓰지 않는다.
- 로그인 없는 접근과 타 계정의 직접 API/사진 접근이 거부된다.
- 내보내기·복원 후 날짜·사진 순서·참조 관계가 일치한다.
- 필요한 빌드·타입 검사·핵심 동작 테스트를 실행하고 실패/미실행을 숨기지 않는다. skip을 통과로 기록하지 않는다.

## 14. 사용자와 협업할 때

사용자는 개발자이며 직접 요구사항을 정하고 화면을 다듬는 데 관심이 많다. 바꾸고 싶은 점을 구체적으로 말하면 그 범위를 반영하고 이미 합의한 구조를 지킨다. '감성 앱'이라는 말만으로 장식을 더하지 않는다. 작동하는 시안을 먼저 보여주고 실제 사용에서 개선하는 방식을 선호한다.

한국어로 결과·확인한 동작·남은 제한을 간결하게 전달한다. 애매한 정책은 질문하되 이미 정한 내용을 다시 묻지 않는다. 가상 동작과 실제 연동, 로컬 저장과 서버 저장을 명확히 구분한다.
