# triplog UI 설계

경로는 저장소 루트 기준이다. 먼저 `AGENTS.md`, `docs/design/DESIGN_SYSTEM.md`, `docs/design/DECISIONS.md`를 읽는다. 기능 범위는 `docs/PRD.md`, `docs/CODEX_HANDOFF.md`, `docs/DECISIONS.md`, 관련 GitHub Issue와 #12를 확인한다. 결정된 것과 제안·미구현을 구분한다.

1. 현재 컴포넌트·스타일·에셋·데이터 계약을 조사하고 해당 화면의 주요 행동, 지켜야 할 동작, 변경할 파일 범위를 짧게 정리한다. 기존 변경·로고·인증·API·현지 날짜·기록을 보존한다. 문서만으로 실제 저장·지도 연동을 가정하지 않는다.
2. 최대 3가지 방향을 제시한다. 방향별로 정보 구조·레이아웃·탐색·상호작용·시각 위계 중 최소 2개가 달라야 한다. 같은 현실적인 가상 기록·같은 화면 크기를 사용하고 가능하면 비교 가능한 정적 목업/미리보기를 만든다. 사진·개인 기록·외부 원본을 임의로 공개하지 않는다. 색만 바꾼 안은 만들지 않는다.
3. 각 안의 주요 행동, 구조 차이, 장점·단점·작은 화면 제약과 추천 이유를 설명한다. 사용자 선택·승인 전 대규모 구현을 진행하지 않는다. 기존에 승인된 방향·범위라면 재승인을 요청하지 않는다. 작은 버그·간격 수정은 불필요한 다안 비교 없이 진행한다.
4. 승인된 방향의 최소 구현 계획을 제시한다. 기존 토큰·컴포넌트 재사용, 변경 파일, 상태(Loading/Empty/Error·입력/저장 실패), 필요한 검증을 포함한다. 새 스타일 값은 이유를 기록하고 중요한 결정만 `docs/design/DECISIONS.md`에 남긴다. 새 라이브러리는 이유·대안을 제시하고 승인 후 설치한다.
5. 구현 요청까지 승인되었다면 해당 범위만 구현하고 `triplog-ui-review` 기준으로 검토·개선한다. 설계/계획만 요청된 경우 구현하지 않는다. Critical → Major → Minor 순으로 문제를 해결하고 재검토한다.

브랜드는 흰 바탕·크림 포인트·SUIT·얇은 선·사진/글 중심이다. 주간 7일·+N개 접근, 월간 세로선 없는 기간 밴드, 다이어리·여행·지도 메뉴를 유지한다. #22의 세로형 배치는 미확정이다. 동행자·이동편은 #4·#23의 범위를 따르고 예약·추천·공유 기능을 추가하지 않는다.

결과는 맥락·방향 비교·추천·승인 대기 사항 또는 승인된 구현 계획을 한국어로 간결하게 전달한다. 실제 UI 변경 시 320/360/390px·데스크톱·낮은 높이·글자 확대·긴 한글·사진 유무·빈/다량 기록·키보드·대비를 검증한다. 브라우저/실기기 검증 여부를 분리하고 미검증을 명시한다.
